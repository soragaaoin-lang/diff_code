# AIを利用する開発手順書・成果物一覧（たたき台）

作成日：2026-10-27 ／ 状態：運用案・未承認

## 1. 前提

利用者が提示した現行工程をもとに、入力・作業・保存物・完了条件を整理した案。社内の正式手順ではなく、会社の承認規程・文書様式を優先する。特定企業の実績やplismの開発経験を根拠とするものではない。

AIは調査・作成・照合・修正を補助する。業務仕様の決定と正式承認は担当者が行う。IDE・CLIのどちらでも同じ成果物を利用する。

以下の「デプロイ」は開発・検証環境への配置を想定。本番リリースは別手順とし、マージ完了と本番公開を区別する。

## 2. 保存の基本

- Jira：目的、担当、状態、受入条件、関連成果物へのリンク。
- 指定の文書管理先：正式な要件・変更仕様・機能仕様と承認記録。
- Git：コード、テストコード、評価スクリプト、チーム共有するAI向け設定。
- CI／指定の証跡保存先：テスト・デプロイ・評価結果。大きなログや動画はここに保存し、GitやJiraからリンクする。
- AI向けに仕様をMarkdown化する場合、正本のURL・版・取得日を記載し、参照用であると明示する。
- 同じ情報を工程ごとに別ファイルへ転記しない。会社指定の正本を更新し、リンクを共有する。
- AI会話全文の保存は必須にしない。判断、未決事項、採用した指示、検証結果を残す。保存規程があれば従う。
- チケットIDを共通キーとし、仕様の版・PR・コミット・検証環境・証跡を結び付ける。

## 3. 工程別の手順と成果物

完了条件は提案。承認者と承認方法は既存の社内ルールに合わせる。

| 段階 | 入力 | 作業（AIは調査・下書き・照合を補助） | 保存物・生成物 | 完了条件 |
|---|---|---|---|---|
| 01 仕様検討・要件定義 | 依頼、課題、現行仕様 | 目的、対象・対象外、制約、受入条件を整理 | 要件、未決事項、決定理由 | 目的・範囲が合意され、未決事項の扱いが決まる |
| 02 要件レビュー | 要件と関連仕様 | 妥当性・影響・抜けを確認 | 指摘、回答、修正版、対象版と正式承認 | 必須指摘を解決し承認される |
| 03 変更仕様書作成・レビュー | 承認済み要件 | 変更前後、互換性、影響範囲を記述・確認 | 変更仕様書、改版履歴、指摘対応、承認 | 変更内容が承認される |
| 04 機能仕様書作成・レビュー | 変更仕様、関連コード | 入出力・処理・例外・権限・境界条件を具体化 | 機能仕様書、確認事項と回答、設計判断、承認 | 実装に必要な判断が解決、または対象外と明示される |
| 05 Jira作成・レビュー | 承認済み仕様 | 作業、受入条件、依存関係、担当を整理 | Jira、仕様のURLと版、依存チケット、レビュー記録 | 作業単位と完了条件が明確になる |
| 06 テスト設計 | 仕様、受入条件 | 正常・異常・境界・回帰を設計 | ケースID、条件、入力、期待結果、要件との対応、レビュー記録 | 期待結果と実施方法が確認される |
| 07 実装準備 | Jira、仕様、テスト設計、現行コード | 関連箇所と類似実装を調査し方針を決める | 変更予定箇所、実装方針、根拠、未決事項、テスト方法、基点コミット | 変更範囲と検証方法が分かり、必要な業務判断が済む |
| 08 実装 | 確認済み方針・仕様 | 実装と必要なテストを作成 | コード、unit／E2E等のテストコード、文書差分 | 対象の実装とローカルで可能な確認が終わる |
| 09 テスト・AIレビュー・自己レビュー | 差分、仕様、テスト設計 | テスト実行、仕様照合、AI指摘と全差分を本人が確認 | コマンドと結果、指摘の採否・理由、自己レビュー結果 | 必須確認が通り、未解決事項が明示される |
| 10 検証環境デプロイ・動作確認 | 検証済みコミット、環境設定 | 配置し、対象ケースを確認 | 対象SHA／ビルドID、環境、日時、配置結果、ケース別結果・証跡 | レビュー対象と検証対象が一致し、必須ケースが通る |
| 11 コードレビュー | PR、仕様、テスト結果、動作証跡 | 人が正しさ・設計・影響を確認 | 指摘、対応方針、未解決事項、正式な承認状態 | 通過なら13へ。修正なら12へ |
| 12 指摘対応・再検証 | 指摘と対応方針 | 必要な仕様・コード・テストを修正し09〜11を繰り返す | 対応コミット、仕様の改版・再承認、再実行結果、更新証跡 | 修正後の内容に必要な承認と検証がそろう |
| 13 マージ依頼 | 承認済みPRと証跡 | CI、依存PR、マージ順を確認して依頼 | 依頼・承認、対象ブランチとSHA、依存関係 | 所定のマージ条件を満たす |
| 14 競合解消・再提出（必要時） | 最新の統合先、競合差分 | 両方の変更意図を確認して解消し、影響に応じて再検証・再レビュー | 基点、解消後の差分とSHA、結果、更新された承認 | 統合後の内容に必要な検証と承認がそろう |
| 15 マージ完了 | マージ可能なPR | 統合し、統合後のCIを確認 | PR、マージ先、マージ後SHA、CI結果 | 統合後の必須チェックが通る |
| 16 第三者評価スクリプト作成・実施 | 仕様、評価項目、マージ済みコード | 第三者が期待結果とスクリプトを確認して評価 | スクリプト、データ、実行手順、対象SHA、環境、結果、不具合票 | 評価を記録し、不具合の扱いが決まる |
| 17 完了整理 | 全成果物と評価結果 | リンク・版・残件を整理してJira更新 | 成果物索引、残件と担当、完了記録 | 所定の完了条件を満たし追跡可能になる |

第三者評価の実行がマージ後でも、評価項目と合否基準は工程06から準備し、第三者が確認することを推奨する。実装だけから期待結果を逆算しない。

## 4. 修正と差し戻し

| 指摘の種類 | 対応 |
|---|---|
| 実装が仕様と違う | コードと関連テストを修正。実装に合わせて仕様を変えない |
| 仕様の曖昧さ・矛盾 | 判断を確認し、必要な仕様改版と承認後に実装へ反映 |
| 新しい要求・対象範囲の拡大 | 変更として影響・工数・日程を判断し、要件・仕様・Jira等へ反映 |
| 内部設計・可読性 | 動作への影響を確認してコード・必要な設計文書を修正 |

仕様変更時は、依存するテスト設計、Jira、実装、AI向け参照資料も更新する。必要な再承認を受ける。

コード変更後は、変更前の動作証跡を新しいコードの証跡として扱わない。影響に応じて再テスト・再デプロイ・動作確認し、対象SHAを記録する。

競合解消では、文字上の競合解消と動作の整合を別に確認する。承認後に差分が変わった場合は、社内基準に応じて再レビューする。

第三者評価で不具合が見つかったら不具合票を作り、必要な仕様判断・実装修正・再レビュー・マージ・再評価へ戻る。

## 5. 保存先・正本の対応

ファイル名は例。既存様式に同じ情報がある場合は新規作成しない。

| 情報 | 正本 | 作業用ファイル名の例 |
|---|---|---|
| 状態・担当・受入条件・成果物索引 | Jira | index.md（リンク中心） |
| 要件・変更仕様・機能仕様 | 会社指定の文書管理先 | spec-reference.md（参照用） |
| 実装方針・判断根拠 | 指定の設計管理先／PR | implementation-plan.md、decisions.md |
| テスト設計 | 指定のテスト管理先 | test-plan.md |
| 実装・テスト・評価スクリプト | Git | 既存の構成に従う |
| レビューと承認 | 指定の文書管理／Jira／PR | 必要なら対応の要約のみ |
| テスト・配置・評価結果 | CI／指定の証跡保存先 | validation-summary.mdに結果要約とリンク |
| 確認済みの共通知識 | チーム共有先／Git | .kiro/steering/配下の関連文書 |
| 自動化設定 | チーム共有先／Git | 利用可能なKiroのagent／workflow／hook設定 |

証跡の保存期間・アクセス権は社内ルールに従う。文書内の「承認済み」という記載だけで正式承認を代替しない。

## 6. 一つのチケットに残す最小セット

1. Jira：目的、範囲、受入条件、担当、成果物へのリンク。
2. 参照仕様：正本URLと版。AI向け変換があれば変換元を明示。
3. 実装方針：対象箇所、方法、根拠、未決事項。小さな変更ならPR本文にまとめる。
4. テスト：期待結果と、対象コードの版に結び付いた実行結果。
5. レビュー：指摘、採否・理由、対応コミット、承認。
6. 統合・評価：マージ後SHA、第三者評価結果、残件。

工程ごとにファイルを増やすのではなく、これらを一つの索引からたどれるようにする。

## 8. Kiroで進める際の補足

- 作業開始時：チケット、仕様の版、対象範囲、共通ルール、テスト方法を渡す。
- 工程終了時：変更した成果物、実行した検証と結果、未実行項目、未決事項を報告させる。
- 推測と確認済み事項を区別し、業務判断が必要なら停止する。
- 自動化する場合も、この手順書の入力・出力・完了条件を使う。正式承認を飛ばさない。
- 最初は実装→テスト→AIレビュー→修正などの明確な範囲で試す。
- 自動再試行の上限と停止条件を決め、同じ失敗の反復や対象範囲の拡大は人へ戻す。
- 共通ルール化は妥当性を確認してから行い、一度の指摘を全体へ無条件に適用しない。

この補足は運用方針であり、Kiroの設定仕様や現在の環境での利用可否を保証するものではない。
